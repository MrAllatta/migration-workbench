# 0.6 — Profiler release

**Theme:** Profiler ingestion hardening and column analysis infrastructure.

Three issues from the Long Season Farm corpus profiling pass, all profiler-side,
bundled into a themed release. Implemented outside-in: quick wins first, then
the heavier column analysis.

## Phase 1 — Reserved-character sanitization (Issue #2)

### What

A `sanitize_tab_name(name: str) -> str` utility that replaces reserved
characters with underscore (`_`) and logs a warning on each replacement.

### Character set

`|` `:` `\` `/` `*` `?` `"` `<` `>` `%`

These are characters invalid in YAML bare strings, Python identifiers, or
filesystem paths.

### Where applied

- `connectors/google_provider.py` — `shape_sheet_structure()` and tab listing
  from the Sheets API
- `connectors/coda.py` — `shape_coda_table_structure()` and table listing from
  the Coda API
- `profile_preflight.py` — validation gate that warns the operator when tabs
  are being renamed
- `cohort_corpus.py` / `coda_corpus.py` — inventory rows processing

### Design

```python
def sanitize_tab_name(name: str) -> str:
    """Replace reserved characters in tab names with underscore.

    Logs a warning when replacement occurs so the operator is aware of the
    renamed tab.

    Args:
        name: Raw tab title from the provider API.

    Returns:
        str: Sanitized tab name safe for YAML keys, Python identifiers, and
            filesystem paths.
    """
    _RESERVED_CHARS = re.compile(r'[|:\\/*?"<>%]')
    sanitized = _RESERVED_CHARS.sub('_', name)
    if sanitized != name:
        logger.warning("Tab name sanitized: %r -> %r", name, sanitized)
    return sanitized
```

### Non-goals

- Configurable character maps or per-deployment overrides.
- Preservation of original name for display purposes (raw API data is still
  available upstream).

## Phase 2 — Tab exclusion by pattern (Issue #1)

### What

A `tab_exclude_patterns` list in the scoring heuristics config. Each entry
specifies a regex pattern and a penalty weight. When a tab title matches, the
penalty is subtracted from the tab's raw score.

### Config shape

```json
{
    "heuristics": {
        "tab_score": {
            "tab_exclude_patterns": [
                {"pattern": "\\b\\d{3}\\b", "penalty": -5}
            ]
        }
    }
}
```

### Integration surface

- `profiler/tools/cohort_corpus.py`:
  - `_normalize_tab_heuristics()` reads the `tab_exclude_patterns` array and
    compiles regexes.
  - `score_tab()` accepts the compiled matchers and accumulates penalty for
    each matching pattern.
- Tabs still appear in the shortlist (with reduced score) for manual override.
- Product repo configures corpus-specific patterns for workbook code
  cross-references or other derived-tab naming conventions.

### Non-goals

- Universal catch-all `\b\d{3}\b` heuristic baked into the chassis.
- Coda corpus equivalent (Coda docs don't use the convention this addresses).

## Phase 3 — Column formula structure analysis (Issue #3)

### What

A formula-analysis pass that examines cell-level formula patterns in each
column and assigns a classification.

### Column classifications

| Class | Meaning |
|-------|---------|
| `raw` | Cells contain manually entered values, no formulas |
| `row_formula` | Each cell has its own per-row formula (e.g. `=A2+B2`) |
| `expansion_formula` | Column governed by a single expansion construct (ARRAYFORMULA, QUERY, FILTER, SORT, UNIQUE) filling many cells |
| `hybrid` | Column has both raw data and formulas |
| `empty` | Mostly empty, headers, or formatting only |

### Key distinction

The critical signal is formula *structure*, not formula *presence*:

- A single `ARRAYFORMULA(A2:A10000)` in row 1 → one expansion governs 9999
  cells → `expansion_formula`
- 10000 individual `=A2+B2` formulas (one per cell) → independent per-row
  formulas → `row_formula`
- A column where 30 cells have typed values and 20 have `=IF(...)` formulas →
  `hybrid`

### Artifact integration

The classification flows into existing pipeline artifacts:

1. **`structure.json`** — each column entry gains a `formula_pattern` field.
2. **Tab scoring** — scoring heuristics gain an `expansion_formula_ratio`
   metric with configurable weight. Tabs with high expansion formula ratios
   receive a penalty.
3. **Schema contract field annotation** — each proposed field carries a
   `formula_pattern` annotation. The chassis produces the data; product repo
   configures how each class maps to generated code (model field vs `@property`
   vs exclusion).
4. **View manifest** — classification feeds the `editable_fields` /
   `computed_fields` split already present in `view_manifest.py`.

### Chassis vs product policy boundary

The chassis **produces the classification data** at profiling time. It does
**not** hardcode what each class means for Django model generation. The product
repo's config decides which classes map to model fields vs `@property` vs
exclusion.

## Out of scope for 0.6

- Runtime formula evaluation or dependency graph.
- Detecting circular references in formulas.
- Import pipeline transforms for formula columns.
- Configurable character maps for sanitization.
- Coda corpus equivalent for cross-reference detection.

## Acceptance criteria

1. Tab names containing reserved characters (`|`, `:`, `\`, etc.) are
   automatically replaced with underscore at ingestion, with a logged warning.
2. Tabs can be excluded from selection by configuring regex patterns with
   negative weight penalties in the scoring heuristics config.
3. Columns in `structure.json` carry a `formula_pattern` classification.
4. Tab scoring incorporates `expansion_formula_ratio` with configurable weight.
5. Schema contract fields carry `formula_pattern` annotation.
6. Existing tests pass; new tests cover sanitization, pattern exclusion, and
   formula classification.
