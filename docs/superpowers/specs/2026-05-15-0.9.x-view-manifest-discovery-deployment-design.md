# 0.9.x — View Manifest, Discovery & Deployment

**Date:** 2026-05-15
**Status:** Approved

## Summary

Close the schema-design loop and ship production deployment. Four features:

1. **View manifest integration** — exercise `editable_fields`, `computed_fields`,
   `filterable_by` end-to-end in admin generation, with `status_field` override.
2. **Discovery interview pipeline hardening** — cover the round-trip
   (`generate_discovery_interview` → fill → `merge_discovery_notes`) with
   snapshot and integration tests.
3. **Drift check wiring** — `wb drift check` command that re-profiles a source
   and diffs the resulting contract against a baseline, for periodic CI use.
4. **Production deployment on Fly.io** — complete the live deploy path
   (`wb deploy <space> --env production`) and wiring into CI.

## 1. View manifest integration

### Problem

The admin generator already reads `editable_fields`, `computed_fields`,
`filterable_by`, and `status_field` from the view manifest, but:

- `status_field` is inferred by `_infer_status_field()` and only set during
  scaffolding — there is no way to override it post-scaffold in the YAML.
- The round-trip (scaffold manifest → generate admin) has no integration test
  that verifies manifest fields actually appear in the generated admin output.
- Discovery notes that update `status_field` via the manifest don't flow through
  to admin generation because `status_field` is not part of the merge pipeline.

### Design

#### 1a. `status_field` override in view manifest YAML

The view manifest already supports `status_field` at the view level. The
manifest builder infers a value; operators can hand-edit the YAML to change it
or set it to `null / ~` to suppress status questions. This is already working
— the manifest YAML stores `status_field` as an optional string.

**What needs fixing:** The admin generator does not use `status_field` from the
manifest for anything. The `status_field` should influence `list_filter`
ordering (put the status field first) and should be noted in admin class
docstrings or as a comment. Additionally, `status_field` values discovered
through the interview pipeline need to flow back into admin configuration.

**Changes:**

- `admin_generator._pick_filter_fields()`: when `status_field` is set on the
  view entry, promote it to the front of the `list_filter` list if it is not
  already present.
- `admin_generator._render_admin_class()`: emit a comment above the admin
  class noting the status field when present.
- Add `status_field` as an optional admin `status_field` hint in generated
  admin class for developer reference.
- Update `_build_view_entry()` docstring to clarify that `status_field` is
  intended for operator override.

#### 1b. Integration test: manifest → admin

Add a test that constructs a view manifest with explicit fields, runs
`render_admin_py()` with a matching contract, and asserts:

- `editable_fields` appear in `list_display`
- `computed_fields` appear in `readonly_fields`
- `filterable_by` appear in `list_filter`
- `status_field` appears as first entry in `list_filter` when present
- Contract `admin.list_editable` and `autocomplete_fields` are respected
- Manifest fields take priority over pure-contract inference

#### 1c. `_infer_status_field` override via discovery

`apply_discovery_patch()` does not currently write `status_field` back into
view entries. Add a new question type to the discovery interview:

```
<!-- q: status_override tab=Orders field=status -->
- Should the status field for this view be different from the inferred one?  > _
```

This question only appears when `status_field` was inferred (non-null). The
parser extracts the answer and `apply_discovery_patch()` writes
`status_field` on the view entry when the operator provides a different field
name, or clears it to `null` when the operator writes `none` or `clear`.

## 2. Discovery interview pipeline hardening

### Problem

The discovery pipeline (render → fill → parse → merge) has unit tests but no
integration test exercising the full round-trip with a realistic manifest.

### Design

#### 2a. Round-trip integration test

Add a test that:

1. Builds a view manifest from a structure fixture (3+ views, one hidden).
2. Renders an interview.
3. Fills the interview with realistic answers (not placeholder).
4. Parses the filled interview.
5. Merges the patch into the manifest.
6. Generates admin from the merged manifest + contract.
7. Asserts the merged manifest's `role_hints`, `weekly_actions`, and per-view
   `notes` are correct.
8. Asserts the generated admin reflects the merged data.

This test already exists in simplified form (`test_discovery.py`); extend it
to exercise the full pipeline including admin generation.

#### 2b. Failed-parse resilience

`parse_interview()` currently returns empty strings for unanswered questions.
Verify this behaviour remains stable when:

- Questions are re-ordered
- Sections are removed
- Lines are added between questions
- Blank lines are inserted after question markers

Add parameterised test cases for these edge cases.

#### 2c. `render_summary()` enrichment

Add `weekly_workflow` text to the summary output (already accepted as arg but
only included conditionally). Verify the summary reflects all merged data when
`weekly_workflow` is present.

## 3. Drift check wiring

### Problem

`wb contract diff` already compares two contracts but has no mechanism for
periodic re-profiling and automated drift detection. Operators must manually
re-run profiling and diff the results.

### Design

#### 3a. `wb drift check` command

Add a new CLI subcommand that:

1. Loads a baseline contract from a known path (e.g. `build/schema-contract.yaml`).
2. Re-profiles the source (calls `pull_bundle --include-structure` + profile
   + scaffold) to produce a fresh contract.
3. Runs `diff_contracts()` on old vs. new.
4. Runs `migration_safety_checks()` on the diff.
5. Reports results as exit code (0 = no drift, 1 = drift found) with optional
   `--json` output.

For the initial implementation, step 2 is optional — the command can also
accept `--new <path>` to compare an already-profiled contract against the
baseline, which is the CI-friendly path (the CI pipeline re-profiles separately
and passes both paths).

```
wb drift check --baseline PATH [--new PATH] [--json]
```

When `--new` is omitted, `wb drift check` looks for a sibling file
`build/schema-contract-drift.yaml` (or a configured path). If neither exists,
it prints an error and exits 2.

**Implementation:**

- Add `_drift_check()` handler in `deployment/wb_cli.py`.
- The handler delegates entirely to existing
  `workbook.codegen.contract.diff_contracts()` and
  `workbook.codegen.contract.migration_safety_checks()`.
- Add `drift` subparser to `build_parser()`.
- Add a `make drift-check` target that runs `wb drift check --baseline
  build/schema-contract.yaml --json` for CI use.

#### 3b. Drift check Makefile target

Add `drift-check` to Makefile:

```makefile
drift-check:
	$(PYTHON) -m deployment.wb_cli contract diff --old $(CONTRACT) --new $(CONTRACT)/../schema-contract-drift.yaml --json
```

This is a thin wrapper; the real check is `wb drift check` which has proper
exit codes.

## 4. Production deployment on Fly.io

### Problem

`wb deploy` only supports `--dry-run`. The actual deploy path (build, push,
release, health-check) is not wired.

### Design

#### 4a. Live deploy path

Extend `_deploy_dry_run()` and add `_deploy_live()`:

- `_deploy_live()` runs the full deploy sequence:
  1. Validate manifest and secrets
  2. Build the Docker image (via `fly deploy --build-only` or local Docker)
  3. Record a pre-deploy checkpoint in the release store
  4. Run `fly deploy` (or `fly machines run` for machines-based deploys)
  5. Wait for the health check to pass (poll `/healthz`)
  6. Record the release event (outcome=success or failure)
- The `--dry-run` flag remains the default; live deploy requires `--live`.
- Remove the guard that forces `--dry-run` only.

For this iteration, implement the release-store recording and health-gate
pieces. The actual `fly deploy` call is environment-specific and is wired
through the deployment manifest's `build` section.

**Implementation:**

- Add `_deploy_live()` in `wb_cli.py` that:
  1. Validates the manifest.
  2. Resolves space/environment configuration.
  3. Records a `predeploy_checkpoint` release event.
  4. Calls `subprocess.run(["fly", "deploy", ...])` with the resolved config.
  5. Polls the health endpoint until timeout.
  6. Records a success or failure release event.
- Wire `deploy --live` into the parser.
- Add `--timeout` flag for health check polling (default 120s).

#### 4b. Health gate polling

Add `deployment.health` module with `wait_for_healthy()`:

```python
def wait_for_healthy(
    url: str, *, timeout: int = 120, interval: int = 5
) -> bool:
```

Uses `urllib.request.urlopen()` to poll `GET /healthz` until the endpoint
returns 200 or the timeout expires.

#### 4c. Makefile deploy target

```makefile
deploy:
	$(PYTHON) -m deployment.wb_cli deploy $(SPACE) --env $(ENV) --live
```

## Non-goals for 0.9.x

- **Provider interface extraction.** Deferred past v1.0.
- **Postgres at scale.** SQLite-only for now.
- **GUI for contract authoring.** YAML remains the interface.
- **Automated re-profiling in `wb drift check`.** CI calls pull + profile
  separately and passes `--new` to `wb drift check`.
