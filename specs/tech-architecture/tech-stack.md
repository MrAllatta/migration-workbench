# Project Context — migration-workbench

> Generated by `map-codebase` on 2026-07-12. This is the project's Long-Term Memory
> for the codebase itself. Update after significant architectural changes.

## Stack

- **Language / Runtime:** Python 3.11+ (tested on 3.11, 3.12, 3.13). CI pins 3.11.
- **Primary Framework:** Django 5.0–5.2 (`Django>=5.0,<6.0`). The package is a set of
  reusable Django apps consumed by product repos.
- **Packaging:** `setuptools` (`build-system.requires` + `setuptools.build_meta`).
  Wheels built via `python -m build`; PyPI publishing blocked until `1.0.0` due to
  legacy version collisions (see `MEMORY.md` / `docs/roadmap.md`).
- **Critical Libraries:**
  - `google-api-python-client`, `google-auth`, `google-auth-oauthlib` — Google Sheets / Drive.
  - `requests` — Coda REST API and generic HTTP.
  - `PyYAML` — schema contracts, view manifests, deployment manifests, PipelineState.
  - `networkx` — relationship / dependency graphs in profiler.
  - `whitenoise` — static-file serving.
  - `gunicorn` — WSGI server in container.
- **Database:** SQLite by default (WAL pragmas via `connection_created` signal); optional
  PostgreSQL via `DB_ENGINE=postgres`. Production target is Fly.io + SQLite on a
  persistent volume + Litestream replication to Tigris/S3-compatible bucket.
- **Dev / Quality Tooling:**
  - `pytest` + `pytest-django`
  - `black` (formatting)
  - `ruff` (linting)
  - `interrogate` (PEP 257 docstring coverage, threshold 80%)
  - `build`, `twine` (release)
- **Hosting Target:** Fly.io (`fly.toml`, `Dockerfile`, `deploy/spaces.yml`).

## Architecture

`migration-workbench` is a library of **five Django apps** that product repos install
and wire into their own `INSTALLED_APPS`. The root `manage.py` and
`migration_workbench/settings.py` exist only for development, CI, and smoke tests.

```
SourceConfig (JSON)  →  connectors/ProviderRouter  →  GoogleSheetsAdapter | CodaAdapter
                                                              ↓
                                                   raw rows + structure metadata
                                                              ↓
                                                  profiler/ (read-only profiling)
                                                              ↓
                                            bundle JSON / CSVs / profile snapshots
                                                              ↓
                                       workbook/ (schema contract + codegen)
                                                              ↓
                              schema-contract.yaml, view-manifest.yaml, models.py, admin.py, import.py
                                                              ↓
                                       importer/BaseImportCommand (preflight/apply)
                                                              ↓
                                              summary JSON artifact + DB mutations
                                                              ↓
                                    deployment/wb CLI (manifest lint, deploy dry-run/live)
```

### Five apps

| App | Responsibility | Key Entry Points |
|-----|---------------|------------------|
| `connectors` | Provider adapters (Google Sheets, Coda). Abstract `ProviderAdapter` routed by `build_provider_adapter`. | `connectors/base.py`, `connectors/router.py`, `connectors/google_provider.py`, `connectors/coda.py`, `connectors/coda_source.py` |
| `profiler` | Read-only source inspection, tab scoring, corpus pipelines, `PipelineState` checkpointing. | `profiler/tools/pipeline_state.py`, `profiler/tools/cohort_corpus.py`, `profiler/tools/coda_corpus.py`, `profiler/management/commands/run_pipeline_state.py` |
| `importer` | `BaseImportCommand` chassis, preflight/apply modes, tiered atomic transactions, summary JSON. | `importer/base.py`, `importer/chassis.py`, `importer/bundle_reader.py`, `importer/summary.py` |
| `workbook` | Schema contract, field mapping, view manifest, discovery interview, codegen (models/admin/import/views). | `workbook/schema_contract.py`, `workbook/view_manifest.py`, `workbook/discovery.py`, `workbook/codegen/*.py`, `workbook/management/commands/` |
| `deployment` | Manifest validation, release store, `wb` CLI, health-check polling. | `deployment/wb_cli.py`, `deployment/manifest.py`, `deployment/release_store.py` |

### Patterns observed

- **Provider Adapter / Strategy:** `ProviderAdapter` ABC with `fetch_tab_rows` and
  optional `fetch_tab_structure`. Provider picked from bundle config `"provider"` key.
- **Pipeline as checkpointed phases:** `PipelineState` enforces ordering across
  `discover → score_and_select → deep_profile → derive_contracts → scan_formulas → validate`.
  Large artifacts externalized to JSON and referenced by `_artifact` keys in YAML.
- **Contract layering:** Three interacting contract documents:
  1. **Schema contract** (data model)
  2. **View manifest** + **interaction contract** (UI / workflow)
  3. **Pipeline manifest** (execution plan for import)
- **Codegen from YAML:** `models.py`, `admin.py`, `import.py`, and view/template/url
  artifacts are generated from reviewed YAML, then hand-hardened in product repos.
- **Vertical templates:** Domain presets (`workbook/verticals/farm/`, `example/`)
  merged into schema contracts for known domains.
- **Command-oriented entry points:** Most user-facing behavior is exposed via Django
  management commands and the `wb` console script.

## Conventions (Observed)

- **Code style:** Black formatting, Ruff linting. Google-style docstrings (`Args:`,
  `Returns:`, `Raises:`). `interrogate` enforced at 80%.
- **Naming:** snake_case for Python identifiers, PascalCase for Django models.
  Project explicitly bans single-letter names and abstract placeholders.
- **Commits:** Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `ci:`).
- **Versioning:** Semver. Package version (`pyproject.toml`) and schema versions
  (e.g., `PipelineState.version`) are kept independent.
- **Error handling:** `workbench.exceptions.UserFacingError` carries `message`,
  optional `action`, `valid_values`, and `check_id`. Management commands use
  `command_error()` to wrap these in Django `CommandError`.
- **API / data shapes:**
  - Management commands print human text; many accept `--json` for machine output.
  - Summary artifacts are JSON with top-level `status` (`"ok"` / `"failed"`) and
    `results.totals`.
  - YAML used for contracts/manifests; JSON for profiler artifacts.
- **Type system:** Python 3.11 union syntax (`str | None`), dataclasses, type hints
  on public functions, but **no static type checker is enforced**.
- **Testing:** pytest-django. Tests live in per-app `tests/` directories. ~1,760 tests
  collected. Fixtures use `call_command`, `tmp_path`, and model fixtures.
- **Observability:** Standard library `logging`. `/healthz` endpoint returns JSON with
  DB ping + `RELEASE_ID`. No structured logging schema, no metrics, no tracing.
- **CI / gate:** `.github/workflows/ci.yml` runs `ruff check`, `ruff format --check`,
  `make chassis-gate`, and `make doc-coverage`. `make chassis-gate` is the local
  authoritative gate: migrate, pytest across all app test dirs, manifest lint,
  health smoke, and many command smoke tests.
- **Branch / release discipline:** Feature branches `feat/<slug>`; agent commits locally;
  human pushes. `make release VERSION=x.y.z` enforces version/changelog/tag alignment.
  Pre-commit hooks are explicitly avoided; CI is the gate.

## Signals / Active Considerations

### Debt Hotspots

1. **Large files carrying too many responsibilities:**
   - `profiler/tools/pipeline_state.py` (~3,000 lines) — checkpoint lifecycle, migrations,
     phase orchestration, contract derivation, signal output, validation.
   - `profiler/tools/cohort_corpus.py` (~2,000 lines) and `profiler/tools/coda_corpus.py`
     — multi-doc profiling orchestration + heuristic scoring.
   - `deployment/wb_cli.py` (~1,400 lines) — CLI surface, contract review, deploy,
     vertical/ecosystem commands, generation helpers.
   - `workbook/codegen/admin_generator.py` (~1,500 lines) — admin rendering logic.

2. **Broad exception handling is pervasive.** Many management commands and profiler
   tools use bare `except Exception` (often with `# noqa: BLE001`) to keep pipelines
   resilient against flaky external APIs. This makes failure modes hard to reason about
   and can swallow programming errors.

3. **Lint drift.** Current working tree: `ruff check .` reports 12 errors (mostly E402)
   and `ruff format --check .` reports ~43 files that would be reformatted. The CI
   workflow *does* run both, so either CI is currently red or local tool defaults have
   diverged from the CI environment. This is a consistency gap that should be resolved.

### Consistency Gaps

4. **No pre-commit / local lint gate.** The project deliberately avoids pre-commit hooks,
   relying on CI. This works only if CI is green; drift creates a trust problem.

5. **Type hints present but not enforced.** There is no `mypy`, `pyright`, or `basedpyright`
   in the dev dependencies, so type annotations are documentation-only.

6. **Two parallel versioning stories.** The package uses a collision-free local line
   (`0.5.3 → 0.7.2 …`) because legacy `0.1.0–0.9.3` releases are blocked on PyPI. New
   adopters may be confused by the gap between git tags and PyPI versions until `1.0.0`.

### Integration Points

7. **External provider APIs are central.** Google Sheets/Drive and Coda are not wrapped
   behind a stable facade beyond `ProviderAdapter`; rate limiting, retries, and auth are
   provider-specific. Adding a third provider (Airtable, Notion, etc.) requires a new
   adapter + structure shaping + profiler commands.

8. **Product-repo coupling is intentionally tight at codegen boundaries.** Generated
   files (`*_auto.py`) are overwritten by commands; product repos must separate hand edits
   from generated files. Recent work had to split checklist vs. dashboard generated files
   manually because the generator always writes to `views_auto.py`/`urls_auto.py`.

### Recent / Active Directions

9. **Track B: UI codegen extraction from farm.** Checklist, landing, and dashboard
   archetypes now generate views, templates, and URL patterns. The generator currently
   lacks per-archetype output module names; product repos must manually rename files
   when mixing archetypes.

10. **Vertical template maturity.** Only `farm` and `example` verticals exist. The
    scoring/matching logic is heuristic-driven and likely needs hardening for new
    domains.

11. **Real-data validation rule.** Track B patches and Track A minors require a real-data
    test in a product repo, not just workbench unit tests. This makes release gating
    dependent on external repo state and env vars (`CODA_API_TOKEN`, Google credentials).

## When to Re-run This Analysis

- After a major refactor of the five-app boundary.
- After adding a new provider adapter or a new contract layer.
- After introducing a static type checker, structured logging, or a new quality gate.
- When onboarding a new contributor or agent to the project.
